# 11.17: [OpenAI 실습]

## 사전 준비

- 환경 설정: `.env` 파일을 `20261117/mentor` 폴더에 배치하고 필요한 라이브러리 설치 완료
- 실행 명령어: `python main.py --source live --allow-paid`
    - `-source live`: 실제 API 호출
    - `-allow-paid`: 유료 API 호출을 명시적으로 허용
    - 실수로 API를 호출해 비용이 발생하는 것을 방지하기 위한 설정
- API 키 설정: `.env`의 `OPENAI_API_KEY=` 뒤에 발급받은 키값만 입력

## 1교시 — 첫 API 호출

- 실습 목적: Python에서 OpenAI API를 직접 호출하고 응답받기
- 핵심: 실제 API 호출 시 `-allow-paid` 옵션을 추가해야 실행되도록 설정
    - 실수로 유료 API를 반복 호출하는 것을 방지
    - 실제 서비스에서도 불필요한 API 호출을 막기 위해 별도의 허용 조건을 둘 수 있음

## 2교시 — 구조화된 출력과 응답 검증

### 구조화된 출력 (Structured Output)

- 프롬프트에 단순히 "JSON으로 답해 줘"라고 요청하는 것이 아니라, API 요청 설정에서 출력 형식을 지정하는 방식
- AI가 정해진 데이터 구조에 맞춰 답변하도록 제한

### `response_gate()` — 응답 검증

- 목적: AI의 응답을 실제로 사용해도 되는지 확인
- 검사 순서:
    1. AI가 답변을 거절했는지 확인
    2. 거절하지 않았다면 API의 응답 생성이 완료되었는지 확인
    3. 완료되었다면 실제 답변 텍스트가 있는지 확인
- 거절 여부를 먼저 확인하는 이유: API가 정상적으로 응답 생성을 완료했더라도 AI가 답변을 거절했을 수 있기 때문

핵심: API의 응답 생성 완료와 사용 가능한 답변인지는 별도로 확인해야 한다.

## 3교시 — 스트리밍과 TTFT

### TTFT (Time To First Token)

- 의미: API 요청을 보낸 순간부터 첫 번째 응답 토큰이 도착할 때까지 걸리는 시간
- 목적: 사용자가 얼마나 빨리 첫 응답을 받을 수 있는지 확인하는 지표
- 암기 대상: TTFT는 전체 답변 생성 시간이 아니라 첫 응답까지의 시간

### `receive_event()` — 스트리밍 처리

- 목적: AI가 답변을 조금씩 보내는 동안 텍스트를 저장하고 첫 텍스트 도착 시간을 측정
- 처리 과정:
    1. AI가 보내는 텍스트 조각(`delta`)을 순서대로 저장
    2. 비어 있지 않은 첫 텍스트가 도착하는 순간 TTFT 기록
    3. 최종 이벤트가 도착하면 응답 완료 여부 확인

핵심: 답변을 모두 받은 뒤 TTFT를 계산하는 것이 아니라, 첫 텍스트가 도착한 순간 시간을 기록한다.

## 4교시 — 오류 분류와 재시도

### `classify()` — 오류 분류

- 목적: API 요청에 오류가 발생했을 때 다시 시도할 가치가 있는지 판단
- 오류가 발생했다고 무조건 다시 요청하면 불필요한 API 호출이 발생할 수 있음
- 예시:
    - 일시적인 서버 오류 → 재시도 고려
    - 잘못된 API 키 → 다시 요청해도 해결되지 않으므로 재시도하지 않음

### `delay()` — 재시도 대기 시간 계산

- 목적: 일시적인 오류가 발생했을 때 얼마나 기다린 뒤 다시 요청할지 계산
- 처리 과정:
    1. 재시도까지 기다릴 시간 계산
    2. 전체 작업에 허용된 남은 시간과 비교
    3. 남은 시간 안에 재시도할 수 있으면 대기 후 재요청
    4. 남은 시간을 초과하면 재시도하지 않고 오류 처리

핵심: 오류 종류와 남은 시간을 확인해 불필요한 API 재호출을 방지한다.

## 5교시 — 토큰 사용량과 비용 분석

### `checkpoint_cost()` / `calculate()` — 비용 계산

- 목적: API에서 사용한 토큰 수를 확인하고 예상 비용 계산
- 토큰 계산 시 주의사항:
    - `input_tokens`: 전체 입력 토큰 수
    - `cached_tokens`: 입력 토큰 중 캐시된 부분
    - `output_tokens`: 전체 출력 토큰 수
    - `reasoning_tokens`: 출력 토큰에 포함된 추론 토큰 수

캐시 토큰은 입력 토큰에 이미 포함되어 있으므로 전체 토큰 수를 계산할 때 다시 더하지 않는다.

하지만 일반 입력 토큰과 캐시된 입력 토큰은 요금이 다르므로 비용 계산에서는 구분해야 한다.

### `usage_analysis.json` — `null`과 `0` 구분

| 값 | 의미 | 예시 |
| --- | --- | --- |
| `0` | 실제 값이 0으로 기록됨 | `cached_tokens: 0` → 캐시 토큰 0개 |
| `null` | 값이 없거나 측정되지 않음 | `first_text_ms: null` → 첫 텍스트 도착 시간 미측정 |

핵심: 확인되지 않은 값을 임의로 0으로 바꾸면 실제 사용량이나 비용을 잘못 판단할 수 있다.

## 6교시 — 캐시(Cache)

### KV Cache

- 의미: LLM이 답변을 생성할 때 이전 토큰의 계산 결과를 저장하고 재사용하는 기술
- 작동 방식: 이미 계산한 Key(K)와 Value(V)를 저장해 다음 토큰을 생성할 때 재사용
- 목적: 불필요한 반복 계산을 줄여 답변 생성 속도 개선

### 캐시 처리 방식

- 캐시 재사용 여부는 일반적으로 `if`문으로 조건을 검사해 결정할 수 있음
- 캐시를 사용할 수 없는 상황은 반드시 프로그램을 종료해야 하는 오류가 아니므로, `try-except`로 예외 처리할 필요가 없는 경우가 많음

### `read_cache()` — 저장된 답변 재사용

- 목적: 이전에 저장한 AI 답변을 다시 사용해도 되는지 확인
- 처리 과정:
    1. 저장된 캐시가 존재하는지 확인
    2. 유효기간, 사람의 승인, 사용 범위, 출처 등을 검사
    3. 검증 기준과 답변 내용까지 확인
    4. 모든 조건을 통과하면 재사용하고, 하나라도 실패하면 `None` 반환

### `run.json` — 캐시 재사용 결과

- 모든 조건을 통과하면 `source_mode: app_cache`로 기록
- 이번 실습은 완성된 답변 전체를 재사용하므로 새로운 API 호출과 토큰 사용량이 0

핵심: 캐시가 있다고 무조건 사용하는 것이 아니라, 모든 조건을 통과한 경우에만 재사용한다.

## 7교시 — Model Routing (모델 라우팅)

### `route()` — 모델 선택

- 목적: 실행 목적에 맞는 AI 모델 선택
- 실행 모드:

| 모드 | 의미 | 예시 |
| --- | --- | --- |
| `fast` | 빠른 응답을 우선하는 모델 | 간단한 질문에 빠르게 답변 |
| `quality` | 답변 품질을 우선하는 모델 | 복잡한 질문을 자세히 분석 |
- `fast`, `quality` 이외의 값은 오류 처리
- `quality` 모델은 계정 권한이나 프로그램 설정에 따라 사용이 제한될 수 있음
- 실제 모델 선택은 `checkpoint_choose()` 함수에서 수행

### `comparison_modes()` — 비교 대상 지정

- 목적: 비교할 모델 모드 목록을 반환
- 반환값: `["fast", "quality"]`
- 이 함수는 비교 대상만 지정하며, 실제 모델 호출과 결과 비교는 다른 코드에서 수행

핵심: 모델 선택과 모델 비교는 별개의 작업이며, `comparison_modes()`는 비교할 대상만 반환한다.
