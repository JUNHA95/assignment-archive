# 11.23 RAG · LangChain 학습 정리

## 1. RAG (Retrieval-Augmented Generation)

**[사용 목적]**
- 주로 사내 문서나 데이터베이스의 정보를 활용해 LLM이 답변하도록 할 때 사용한다.

**[의미]**
- 사용자 질문과 관련된 자료를 검색하고, 해당 자료를 근거로 답변을 생성하는 일련의 과정(파이프라인)이다.

### 1-1. Vector DB를 활용하는 RAG

**전체 흐름**

Retriever → Context 구성 → Prompt → Generator(모델 호출) → Validator → 사용자 응답

1. **Retriever (검색)**
   - 질문, 검색 대상, 검색 조건을 바탕으로 관련성이 높은 자료를 찾아 전달한다.
2. **Context Builder (자료 구성)**
   - 검색된 자료 중 LLM에 전달할 자료를 선택하고 정리한다.
   - 필요한 경우 검색된 자료를 모두 포함할 수도 있다.
3. **Prompt (입력 구성)**
   - 사용자 질문 + Context + 답변 규칙을 결합하여 모델에 전달할 입력을 만든다.
4. **Generator (답변 생성)**
   - LLM을 호출하여 답변을 생성한다.
5. **Validator (검증)**
   - 답변이 정해진 규칙과 형식을 지켰는지 확인한다.
   - 제시한 출처가 실제 제공된 자료에 포함되는지 검사한다.
6. **사용자 응답**
   - 검증 결과에 따라 답변을 사용자에게 전달한다.

### 1-2. RDB를 활용하는 RAG

**전체 흐름**

RDB 자료 조회 → Hit 획득 → Context 구성 → Prompt → Generator → Validator → 사용자 응답

- **Document:** 문서의 본문과 출처 등의 정보를 담은 객체
- **Hit:** 검색하거나 조회한 자료 중 질문과 관련된 자료 한 건
- **Context:** Hit을 바탕으로 LLM에 전달할 참고 자료를 정리한 것

※ Vector DB와 RDB는 자료를 찾는 방식이 다르지만, 이후 답변 생성 및 검증 과정은 유사하다. RDB를 사용한다고 반드시 Hit을 생성해야 하는 것은 아니다.

## 2. LangChain

**[의미]**
- LLM 서비스를 개발하기 위한 프레임워크
- 프레임워크란 자주 필요한 기능을 미리 구현하고, 이를 활용하는 방법을 제공하는 개발 도구이다.

**[주요 도구]**
- **LangChain:** 검색, Prompt, LLM 호출 등의 기능을 연결하여 서비스 구현
- **LangGraph:** 여러 단계의 작업과 에이전트의 실행 흐름을 관리
- **LangSmith:** LLM 애플리케이션의 실행 기록 추적, 테스트 및 평가

### 2-1. Chain과 Runnable

- **Chain:** 여러 처리 단계를 순서대로 연결한 것
- **Runnable:** LangChain에서 실행할 수 있는 구성요소 또는 실행 단위
- **RunnableLambda():** 일반 Python 함수를 Runnable로 감싸서 Chain에 연결할 수 있도록 하는 도구
- **`.invoke()`:** Runnable에 입력값 하나를 전달하여 실행하고 결과를 받는 메서드
- **`|`:** 앞 단계의 출력을 다음 단계의 입력으로 연결하는 연산자

**Chain 구성 예시**

```python
chain = (
    retrieve_step
    | context_step
    | prompt
    | chat_model
    | StrOutputParser()
)

result = chain.invoke(question)
```

**처리 과정**

1. `retrieve_step`: 질문과 관련된 자료 검색
2. `context_step`: 검색 결과를 Context로 구성
3. `prompt`: 질문과 Context를 Prompt 형식으로 구성
4. `chat_model`: LLM을 호출하여 답변 생성
5. `StrOutputParser()`: 모델 응답에서 텍스트 추출

※ 각 단계를 별도 Python 파일로 관리할 수도 있으며, 필요에 따라 여러 Chain으로 분리할 수 있다.

## 3. 실습 04 — Hit을 Document로 변환

**[목적]**
- 검색된 Hit을 LangChain에서 사용할 수 있는 Document 객체로 변환한다.

**[핵심 함수]**
- `to_document()`: Hit 한 건을 Document 한 개로 변환
- `hits_to_documents()`: 여러 Hit을 입력 순서대로 Document로 변환하고 목록으로 반환

**전체 흐름**

Hit 목록 → 개별 Document 변환 → `list[Document]` 반환

---

## 4. 실습 05 — Prompt 구성과 Chat Model 호출

**[목적]**
- 사용자 질문과 Context를 Prompt에 전달하고, 모델이 답변을 생성하는 과정을 확인한다.

**[핵심 함수]**
- `make_inputs()`: 사용자 질문과 Context를 Prompt에 전달할 딕셔너리로 구성
- `invoke_pair()`: Prompt와 Chat Model을 순서대로 실행하고, 완성된 Prompt와 모델 응답을 함께 반환

**전체 흐름**

입력 준비 → Prompt 구성 → LLM 답변 생성 → 결과 기록

---

## 5. 실습 06 — Context 구성과 Runnable Chain 실행

**[목적]**
- Document에서 Context와 출처 정보를 준비하고, Prompt와 Structured Model을 연결하여 구조화된 응답을 받는다.

**[핵심 함수]**
- `prepare_context()`: Document에서 Context와 출처 정보를 정리하고 Prompt 입력값 준비
- `run_generation()`: Prompt와 Structured Model을 연결해 실행하고 결과인 `bundle` 반환
- `main()`: 전체 과정을 실행하고 결과를 JSON 파일에 기록

**Bundle의 구성**
- `raw`: 모델의 원본 응답
- `parsed`: 정해진 구조로 변환된 응답
- `parsing_error`: 응답 변환 과정의 오류 정보

**전체 흐름**

Context 준비 → Prompt 구성 → 모델 실행 → 구조화된 응답 반환 → 결과 기록

---

## 6. 실습 07 — Citation 및 응답 검증

**[목적]**
- 답변에서 제시한 출처 ID가 실제 Context에 포함된 출처인지 확인하고, 응답 형식과 상태를 검증한다.

**[핵심 함수]**
- `allowed_source_ids()`: Context에 포함된 Document에서 Citation 검증에 사용할 출처 ID 집합 생성
- `inspect_case()`: `receive_bundle()`을 이용하여 응답 형식과 출처 ID를 검증하고 결과 기록

**전체 흐름**

허용 출처 ID 수집 → 답변의 출처 ID와 비교 → 응답 형식 및 상태 검사 → 검증 결과 기록

### Citation과 Grounding의 차이

- **Citation 검증:** 답변에 제시된 출처 ID가 실제 제공된 출처에 포함되는지 확인한다. 프로그램으로 자동 검사할 수 있다.
- **Grounding 검증:** 답변의 내용이 실제 원문에 근거하고 있는지 확인한다. 사람의 직접 대조 또는 별도의 의미 검증이 필요하다.

**핵심:** Citation 검증에 통과했다고 해서 답변 내용까지 정확하다는 뜻은 아니다.
